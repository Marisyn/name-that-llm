# Name That LLM 比赛洞察（2026-11-18）

来源：`assets/kaggle-sync-name-that-llm/`（overview、data、129 个讨论、1569 个公开 notebook 的 RANKING）、`assets/data/train.csv`、`assets/external/open_pool/ntl_open_pool.parquet`（v15，226,191 行）。本项目尚无提交。

## 1. 赛题要点

- 18 类作者归属（OpenAI 5、Google 4、Anthropic 5、Qwen 1、ZAI 2、Moonshot 1），单段 40–250 词。
- 指标 balanced accuracy；测试 ~4000 段，**各类数量不等，public / private 的类别构成也不同**。
- 划分：public 约 40%（≈1600 段），private 约 60%（≈2400 段，决定最终排名）。评分时 notebook 读到的是完整测试集，联合后处理在两部分上的行为相同，区别只在哪些行计分。
- 划分方式官方未说明。参照 Kaggle 赛后公开的 Jigsaw Agile Community Rules 测试集（`sorenj/jigsaw-agile-community-rules-classification`，solution.csv 带 `Usage` 列）：public 28.9%，与 private 在文件中交错分布；**同一条评论的所有行总在同一边**（8,813 个重复 body，没有一个跨两边）；按评论计，划分是纯随机的（游程 18,742，随机期望 18,657）；没有按规则或标签分层。类推到本赛，划分单位可能是 prompt，但这只是一个先例，不是证据。
- train：150 个 prompt × 18 模型（一个 prompt 缺 claude-fable-5），共 2,699 行。测试 prompt 全部不在 train 中。
- Code competition：9h，离线，可用公开外部数据和模型。截止 2027-01-13（入场 / 合队截止 01-06）。前 10 名各 $5k，6,080 队。

## 2. 当前格局

- 公开 notebook 天花板 **0.702**（24 个 0.702、25 个 0.701，几乎都是同一条 fork 链：lumibee Kiro v44 → lightningv08 0.702）。
- **同一代码重复提交分数波动 0.006–0.012**（如 0.682–0.694）。公开 LB 上 <0.01 的差异基本不能说明问题；从 20 个近似变体中选最高分，乐观偏差约 0.005–0.01（讨论 755215 按 1200 行 public 估算；按实际约 1600 行，约为原值的 0.87 倍）。
- 同一提交的 public 与 private 分数差，单纯抽样噪声的标准差约 0.015（准确率 0.7，1600 / 2400 行；balanced accuracy 会更大一些）。同一份代码重复提交的 0.006–0.012 波动是管线本身的不确定性（同一批行），在 private 上同样存在。
- 单模型：Qwen3-8B LoRA ~0.63，Qwen3-14B ~0.67。分数主要来自数据，不是骨干或集成规模；集成只多 ~0.01。

### 主流单模配方（社区公开信息）

- 骨干：Qwen3-8B / Qwen3-14B / Qwen3.5-9B base，**截断到前 60–70% 的层**（如 8B 取前 24 层，14B 取前 27 层），最终 RMSNorm 关闭。冻结 Qwen3-4B 的逐层探针：第 3 层 0.391，最后一层只有 0.311（750462）。
- 读出：对 6–8 个深度（如 2, 4, …, 24 层）做均值池化，每层一个 LayerNorm，拼接后接线性头输出 18 类；可选再加一个"组内居中"头。
- LoRA r16 / α32，覆盖 q, k, v, o, gate, up, down；max_len 384。
- 两阶段训练：先在 pool 上训 1 epoch（按类加权），再在 train 上训 2 epoch，降低学习率；5 折按 prompt 分组。
- 精度：T4 上 fp16 会溢出，溢出的 batch 用 bf16 重算；训练可放到 Kaggle TPU v5e-8 上用 bf16，速度约为 2×T4 的 14 倍，但排队可能超过 20 小时（754657）。
- 分数：Qwen3-8B ≈ 0.63（OOF 0.622），Qwen3.5-9B ≈ 0.649，Qwen3-14B ≈ 0.65–0.67，自称最好的 0.67–0.68（754860）。编码器类：ModernBERT-large ≈ 0.55，DeBERTa-v3-large ≈ 0.50（759103）。只用 train、不加外部数据时约 0.44–0.47。
- 结论：增益主要来自数据；在一个好的单模之上，集成只多约 0.01。

0.702 公开管线的组成：Qwen / Llama LoRA 读出 + Qwen3-Embedding-8B 五折 + Qwen3.8-27B（3-bit GSQ）LoRA + **GLM-5.3 / GLM-5.3-Flash 真实似然**（IQ3 GGUF，2×T4，只算置信度最低的 top 15%）+ n-gram SVC + "sibling residual" 同族修正 + 排版软规则（禁止的标签 ×0.05）。

## 3. 数据洞察

### 排版指纹（train 实测，含该符号的段落比例）

| --- | --- | --- | --- | --- |
| Claude ×5 | 0.63–0.83 | **0** | **0** | 0.15–0.54 |
| GLM ×2 | ~0.8 | **0** | **0** | 0.34–0.48 |
| Gemini ×4 | **~0** | 0.06–0.31 | ~0 | 0.19–0.28 |
| GPT ×5 | 0.09–0.37 | 0.42–0.53 | 0.07–0.15 | 0.43–0.62 |

族间几乎能靠排版分开，难点全在族内。

### 混淆结构

- Gemini 只和 Gemini 混，GPT 只和 GPT 混。3.7 vs 3.8 Flash 是最难的一对（各约一半对）。
- **GLM-5.3 更像 Claude**：一个 9B 分类器把它判成 Claude 68 次、判成自己 34 次（共 150）。glm-5.3 / glm-5.3-flash / claude-fable-5 是公认的噪声角。打开这个角的手段是 GLM 自身的似然。

### 外部数据（Open Pool v15）

- 226k 行，61 个来源。类别极不均衡：gemini-3.8-flash 23k，**gemini-3.7-flash 只有 3.5k**（10/8 起 3.7 被路由到 3.8，已无法再生成），qwen3.8-max 4.6k。不做类别加权，模型会偏向 3.8。
- 与真实分布的偏差：真实 kimi-k3 很可能开了 reasoning（pool 中 `gen_reasoning=="high"` 的 2.7k 行最像真实数据）；kimi、qwen、claude-opus-4-8 的 pool 识别率只有真实的 46–54%。
- 已发现 284 行错标（其他模型被标成 18 个标签之一），v14 起已移除。按跨源一致性删行反而掉分。
- 来源多样性同样不均：gemini-3.7 只有 5 个来源，qwen 11 个，kimi 13 个，gemini-3.8 有 54 个。

### Pool 来源核查（2026-11-18 本地检查，均为粗检）

- 没有发现明显的"掺水"：标准化后的文本没有一条在不同来源里标成不同标签；记录了实际服务模型（`gen_served_model`）的 85k 行（38%）都和标签一致。其余 62% 无法核对。
- Pool 已经按 train 的排版规律过滤过（例如 Claude / GLM 行里的弯撇号只占 0.07%），所以无法再用排版规律去查错标。GPT 行里的直撇号只有 0.7%，而真实 GPT 是 5.2%，说明过滤也改变了分布。
- **gemini-3.7**：有日期的 3,012 行**全部生成于 10/8 路由切换之后**。用 train-only 的 3.7 / 3.8 二分类器检查（train OOF：3.7 有 43% 被判成 3.8，3.8 有 50%；检测器很弱）：
  - `davidpiln/ntl-vertex-gemini-gen` 是最大的来源（2,007 行，占 3.7 的 2/3），它的 3.7 行和 3.8 行几乎分不开（0.471 / 0.476）；
  - `prvsiyan` 的 3.7 行有 70% 被判成 3.8，比真实 3.8 还高。

  两者都可能是被路由的 3.8，需要用按来源剔除的消融实验来确认。Pool 作者已把另外 10,838 行未核实的 3.7 单独放在 `gemini37_unverified.parquet`。
- **qwen3.8-max**：pool 中无论哪个服务版本（0902 / prime / 未知），被识别为 qwen 的比例都只有 12–17%，真实数据是 31%。问题在整个标签，不在某个版本。
- **最可疑的来源 × 标签**（`fidelity_by_source.csv`，n ≥ 200）：
  - `kilupy/ntl-18-model-corpus`：kimi-k3 只有 1.4% 被判到 Moonshot 这一族（真实 31%），glm-5.3 只有 9.5%（真实 37%）；
  - `kilupy/ntl-claude-family-passages` 和 `adurey` 的 claude-opus-4-8。
  - fidelity < 0.5 的组合共 30 个，涉及 18,776 行。
- 处理原则：按"来源 × 标签"整组判断，不逐行筛选；用按来源剔除的分组 CV 消融来决定降权还是剔除。

### Pool 的使用方式（社区证据）

- **类别不均用加权处理，不靠删数据**：对 pool 做按类加权，让每类总权重相同（GoPain，751370），或者每类设上限（754860）。nlm 系列 stage 1 用 class-weighted loss。删掉 3.7 中可疑来源的行，反而让 3.7 的召回下降。
- **清洗有效**：去掉垃圾文本（数据转储、拒答、开场白）+0.009，再去掉体裁不对的来源，共 +0.027（753779，Open Pool v9 起已做）。按跨源一致性逐行筛选反而有害。
- **按"像不像真实数据"筛选**：753779 用 `style_score` 去掉每类最不像 train 的 30%，结果没有提升（−0.004，最难的 8 类召回 −0.016），损失的多样性比风格更干净带来的收益大。当作样本权重还没人试过，`match_weight` 也没有。kimi 的 reasoning=high 子集同样未经训练验证。
- **去掉 Kaggle Benchmarks 代理生成的约 7 万行**：−0.001，在噪声范围内（753779）。
- **廉价代理指标会误导**：TF-IDF + 线性模型判断"清洗有害"，与 LoRA 的结论相反（753779）。数据取舍要用实际训练的模型类型来验证。上面"来源核查"里的 fidelity 结论也是 TF-IDF 级别的，只能当作疑点清单。
- **v15 的残留**（本地正则粗检，与 train 对比）：API dump、CJK、换行都是 0；拒答、开场白、句末无标点都在 0.03% 以下，匹配到的多为正常行文；markdown 记号 1.26%（train 0.41%，2,852 行）。体裁不对的来源无法用正则检查，只能依赖 v9 的来源级剔除；v11–v15 新增的数据按 append log 只做了格式、长度、截断、排版、与 train 相似度的过滤。
- **仍未解决的 prompt 风格差距**：train 中 30.7% 的段落用 we / our / us，pool 只有 14.9%（清洗前后都一样）。原因在主办方的 prompt 风格，不在垃圾数据。自己生成数据时，prompt 应贴近这种"集体、解释性"的语气。
- **Pool 会让 CV 虚高**：用 pool 训练的模型，分组 CV 比 LB 高 0.03–0.04（750390）。只在都用了 pool 的候选之间比较 CV。
- **预测阶段的均衡**：对只用 pool 训练的 LoRA，Sinkhorn 均衡带来 LB +0.011，CV 几乎不变（750390）。说明 pool 先验的偏差在测试集上真实存在。
- **数据组合的多样性比单个成员的 OOF 更重要**：用同一个 pool 重训的更强成员替换旧成员，OOF 0.569 → 0.605，LB 却 0.651 → 0.647（753177）。

## 4. 已被 LB 证伪的方向

- **硬约束版的测试集联合后处理**（Hungarian 一类一个、居中预测完全替代原始预测、Sinkhorn 强制均衡）：offline 很强（按完整 18 段分组的嵌套 CV 0.6865），LB 只有 0.56，每次都掉 0.009–0.017。说明**隐藏测试中每个 prompt 的段落很少**，类别也不均衡。
- **软版本保留在 0.702 方案中**：TF-IDF 话题词 + 带上限的层次聚类（相似度 ≥0.15、组 ≤18，组大小不固定）；组内居中预测只按 w ≤ 0.5 混入，单段组不处理；软 Sinkhorn 的目标分布 = 0.65 × 模型自身预测分布 + 0.35 × 训练先验，再以 0.3 的权重混入。
- 往强集成里继续加 LoRA 骨干：±0.004，在噪声内。
- 硬层级分类（先判公司，再用族内专家判型号）和族内 gate：在噪声范围内，没有收益（讨论 751722；alexchilton 的 4 个族内 gate 0.559 → 0.559）。公司这一层本来就容易（Gemini 约 98%），错误集中在族内，而且最难的 GLM ↔ Claude 是跨公司的，按公司分层解决不了。
- 软层级保留在 0.702 方案中：sibling residual 保持每族的总概率不变，只在族内（claude / gpt / gemini / glm）按一个族内训练的风格 LR 重新分配；族内前两名越接近，混入越多，强度 0.10。
- 注意：社区里的 "two-stage LoRA" 指先在 pool 上训练、再在 train 上微调，不是层级分类。

## 5. 验证协议

- 必须按 prompt 分组 CV（随机 K 折 0.11–0.22，分组 0.31–0.37）。
- **每个 prompt 只抽 2 段做 OOF 评估**，与 LB 的相关从 0.13 升到 0.91（GoPain）。再加上不均衡的类别抽样来模拟 public / private 差异。
- 最终选提交时以这套 OOF 为准，LB 只作为粗检，并扣掉 0.005–0.01 的选择偏差。

### 含联合后处理时的验证流程（设计，待实现）

1. 按 `prompt_id` 做 5 折，得到全部 2,699 行的 OOF logits。pool 中重新生成 train prompt 的行会造成泄漏；v15 里 `flag_train_prompt_regen`、`flag_near_train_prompt` 已全为 0，换用其他 pool 时要再查。
2. 从 OOF 中**抽样模拟测试批**：对每个 prompt 的每段回答，按模型 k 的保留概率 q_k 独立决定是否保留。
   - 每个 prompt 保留的段数 m_p 随之随机变化（1 到 18 之间，0 段的 prompt 直接不出现）；
   - 各类数量不均也来自同一组 q_k。
   q_k 从 Beta 分布抽取，用它的均值控制平均组大小、用它的离散度控制类别不均程度。固定 m 只作为对照场景。抽样只用 `prompt_id` 和标签，后处理本身只看文本和 logits。
3. 在每个模拟批上**完整跑一遍后处理**：聚类 → 居中 → Sinkhorn，先验只取训练折。分别计算 plain 和 +后处理的 balanced accuracy。
4. 重复 200 次以上，报告**成对差值**的均值和置信区间。
5. 做场景扫描：m ∈ {1, 2, 3, 6, 18}，α ∈ {∞, 5, 1}。某项后处理要保留，需满足：在 m=2 这个主场景下提升，在 m=1、α=1 这类悲观场景下不明显掉分。
6. 后处理的超参（w、Sinkhorn 强度、聚类阈值）要用嵌套方式选：在一部分 prompt 的模拟批上调参，在另一部分上评估。
7. 模拟批只有约 300 行（m=2），比真实测试的 ~4000 行小得多，Sinkhorn 估计出的分布会更不稳。可以混入 pool 文本作为不计分的干扰项，把批扩到约 4000 行。

## 6. 规则边界（STAFF 2026-10-28/29）

- 自行用 API 生成数据**允许**，但总花费超过约一个奖金额（$5k）视为不合理；不要求公开。
- Kaggle 上的公开社区数据集、公开 LoRA 权重都可以用。Benchmarks 代理额度不应用于生成数据（但已用的不追究）。
- 测试时利用测试样本之间的关系（聚类、伪标签等全自动处理）：**允许**。STAFF 2026-11-03 在讨论 752084 中答复："Feel free to explore any relationships in the data that you find useful." 不用这类方法的原因是它在 LB 上掉分（见第 4 节），不是规则限制。

## 7. 可能的突破口（按预期收益排序，均待验证）

1. **候选模型自身的似然**：GLM 似然是 0.684 → 0.69x 的主要来源，但目前只覆盖 15% 的文本、9 万 token。把覆盖率扩到全量（更快的量化或推理、更好的时间分配），或者给其他开源权重候选（Kimi 等，需确认可在 2×T4 / 9h 内跑）也加上似然。
2. **针对性的数据**：在预算内补 kimi（reasoning on）、qwen3.8-max、claude-opus-4-8，以及族内难分的对。格式贴近主办方：单段、去掉整段加粗、40–250 词。gemini-3.7 无法再生成，只能做加权或重采样。
3. **以 0.702 全公开管线为底座**，只做能在"2 段 / prompt + 不均衡"OOF 上稳定 ≥ +0.01 的改动；排版规则保持软约束。
4. 保留一个对类别先验变化鲁棒的版本（不强制均衡）作为 private 保险。

## 8. 工程风险

- 9h 限制下大权重的 `/kaggle/input` 首次读取可能很慢，要留 ~30 分钟余量；scoring rerun 没有日志，用 `KAGGLE_IS_COMPETITION_RERUN` 区分 commit 和 rerun。
- 公开管线依赖几十个第三方数据集挂载，作者删除或改版会导致复现失败，最终提交前应把依赖固定到自己可控的副本。
