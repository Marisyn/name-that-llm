## Content

Many top public notebooks now include the Qwen3.5-9B token-attention head. When I forked the 0.600 notebook unchanged, the scoring run exceeded the runtime limit, although the commit run (3 test rows) finished in 79 minutes. In my logs, loading Qwen3.5-9B took 1,206 s and 618 s, versus about 22 s each in the author's log. Removing only that head (one line plus one input) brought my commit run to 1.08x the author's time, and it scored 0.600.

Tip: before submitting a fork, compare the per-step times in your commit log with the author's. If anything is much slower, fix it first, because the hidden test is much larger than the 3 public rows.

Follow-up with the numbers I promised. Thanks @tanmaymane18 — your mmap explanation matches what I measured.

**Probe notebook (T4 x2, one session):**

| Step | Time |
|---|---|
| Sequential read of /kaggle/input (first 1 GB of one safetensors file) | 169 MB/s |
| Qwen3.5-9B from a **Dataset**, direct `from_pretrained` (same settings as before) | **> 600 s, stopped** (the original public notebook's log: 22 s) |
| Same 19.3 GB folder, `cp -r` to /tmp | 420 s (~46 MB/s) |
| Load from /tmp | 33 s |
| Qwen3-8B attached as a **Kaggle Model**, same session | 19 s |
| Qwen3-14B attached as a **Kaggle Model**, same session | 37 s |

So in that session, a short sequential read was fast, but `from_pretrained` reading directly from the Dataset was extremely slow. Copying first worked around it, and Model-attached weights didn't have the problem in that session.

**Re-uploading as a Kaggle Model, in real runs:** I re-uploaded the 5-fold UltraBERT weights (Apache 2.0, ~3.8 GB) as a private Kaggle Model and changed nothing else.

| UltraBERT load + inference | Time |
|---|---|
| From the Dataset, normal session | 147 s |
| From the Dataset, slow session | 1,856 s |
| From my Model, session with an 88 MB/s startup read test | 41 s |
| From my Model, session with a 39 MB/s startup read test | 225 s |

These rows come from different sessions (I only started logging the read speed with the Model runs), so this is not a controlled comparison.

**Caveats:**
- The probe was a single session. The 169 MB/s was only the first 1 GB of one file, so reading a whole multi-file folder may be slower (the `cp` averaged 46 MB/s). I also couldn't drop the page cache (no permission), so part of the `cp` may have come from cache.
- On the very slow nodes, Model-attached weights were slower too. In full runs, the Qwen3-14B LoRA step (load + inference) took 53 s on a normal node, but 211 s and 405 s on two slow ones. So a Model reduces the problem a lot, but doesn't make you immune to it.

**What I do now:**
1. Attach large weights as Kaggle Models, not Datasets.
2. Log the read speed in the first cell.
3. Run optional parts under a deadline and drop them if it passes, so `submission.parquet` is always written.

Since then my submissions have finished in time, including one on a 39 MB/s node: the commit run took 6,458 s, against 15,367 s for the notebook I started from.
