## Content

A warning for anyone training LoRA members on the 2×T4 machine with `torchrun` and fp16 autocast, which is most of
the two-stage recipes here (as far as I can tell).

My stage-1 run on the Open Pool (124,975 passages, 4,591 steps) trained normally for 1,000 steps (loss 4.81 at step 200, 3.53 at step 1,000;
24 batches skipped as non-finite). After that almost every batch was skipped (3,439 in all), the run finished after
9.1 hours without an error, and every saved LoRA and head tensor was NaN. Stage 2 then predicted one class for every
passage (OOF balanced accuracy 1/18 = 0.056).

My loop skipped a non-finite loss like this:

```python
if not torch.isfinite(loss):
    opt.zero_grad(set_to_none=True)
    (logits.float().sum() * 0.0).backward()   # "so this rank still joins the all-reduce"
    continue
```

NaN times zero is NaN, so this backward sends NaN gradients into the all-reduce, and the other rank, whose own
forward was fine, treats the step as a normal one. I wrote a small CPU benchmark (two gloo ranks, an MLP, NaN
injected into rank 1's activations on known steps, 3 seeds, 300 steps) to see what such skip patterns actually do.
Runs with at least one poisoned step:

| skip pattern | no loss scaler | with GradScaler |
| --- | --- | --- |
| backward of logits × 0, then skip | NaN weights | finite, but the two replicas drift apart; accuracy 0.931 → 0.875 at 20% bad batches |
| the same through `torch.nan_to_num` | NaN weights | same as above |
| skip without a backward on one rank | collective timeout | collective timeout |
| no special case, let GradScaler skip | NaN weights | in sync, but the scale halves on every bad batch (1024 → 9e-16 at 20%) |
| all ranks agree first, then skip together | fine | fine |

With a scaler the drift comes from bookkeeping: the healthy rank halves its loss scale and advances its LR schedule,
the skipping rank does neither, and from then on DDP averages gradients that the two ranks scaled differently. Note
that `nan_to_num` on the logits does not help, because the backward still passes through the NaN activations.

The version that stays clean in every run:

```python
ok = torch.tensor(float(torch.isfinite(loss)), device=device)
dist.all_reduce(ok, op=dist.ReduceOp.MIN)      # every rank takes the same branch
if ok.item() < 1:
    opt.zero_grad(set_to_none=True)
    continue                                   # no backward on any rank
scaler.scale(loss).backward()
...
```

Two cheap extras that would have saved me most of the nine hours: check the trainable parameters for finiteness
every 50 steps and stop (or roll back) when they are not, and refuse to save non-finite stage-1 weights.

One more trap, which cost me my second attempt: I also retried an overflowing fp16 batch in bfloat16 before
skipping it, but only on the rank that overflowed. DDP broadcasts module buffers (Qwen's rotary frequencies, for
one) in every forward, so that rank made one extra collective, and 30 minutes in, the NCCL watchdog stopped the run
with rank 1 waiting in the flag all-reduce. A redo has to be agreed like the skip (all-reduce the flag after the
fp16 forward; if any rank overflowed, all of them redo), and `DistributedDataParallel(..., broadcast_buffers=False)`
is safe when the buffers never change.

The CPU benchmark does not reproduce a real fp16 overflow on a T4, so it shows what the patterns can do rather than
the exact route my first run took.
